## 해석

TODO 4번(비교 조건 맞추기). 같은 라운드 안에서 Quill(g++ `-O3`) → logx `-O2` → logx `-O3`를 번갈아 5라운드 돌렸다. 커밋 안 된 변경은 `cmp_bench.c`의 `CMP_LF_CAP`(큐 슬롯 수 환경변수, 기본 16384) 추가와 `tools/cmp_opt.sh` 신규뿐이다. hot path 코드는 바뀌지 않았다.

**1. `-O3`는 효과가 거의 없다.**

| | `-O2` | `-O3` |
|---|---|---|
| `LFLOG` 숫자 1T p50 / p99.9 (ns) | 89 / 435 | 85 / 414 |
| `LFLOG` 숫자 4T p50 / p99.9 | 126 / 649 | 126 / 685 |
| `LFLOG` 문자열 1T p50 / p99.9 | 134 / 529 | 138 / 542 |
| `LFLOG` 문자열 4T p50 / p99.9 | 174 / 679 | 164 / 615 |
| 처리량 `LFLOG` (큐 16MB) | 2.98 | 2.97 |
| 처리량 `LFLOG_TEXT` | 3.53 | 3.55 |

- 지연 차이는 0~6%이고 라운드 사이 범위가 겹친다. 처리량은 같다.
- 빌드 옵션은 Quill과의 차이(p50 약 8배, 처리량 0.64배)를 설명하지 못한다.

**2. 큐를 키우면 처리량이 오히려 떨어진다.**

| 큐 (슬롯 수, 메모리) | `-O2` | `-O3` |
|---|---|---|
| 16384, 약 16MB (기본) | 2.98 | 2.97 |
| 131072, 약 128MB (Quill 이 이 측정에서 커진 최종 크기) | 2.62 | 2.41 |
| 4194304, 약 4GB (400만 줄이 다 들어가 큐가 차지 않음) | 2.58 | 2.27 |

- 큐가 차지 않아도 빨라지지 않는다. 처리량 상한은 큐가 차서 막히는 데 있지 않고, 로깅 스레드가 소비하는 속도에 있다. 이는 TODO 3번(`%g`)의 가설과 맞는다.
- 큐가 커질수록 느려지는 것은 생산자가 새 페이지를 처음 건드릴 때의 페이지 폴트와 TLB·캐시 미스로 보인다(아직 안 잼). 16MB 큐는 계속 재사용되어 캐시에 따뜻하게 남는다.
- 큰 큐에서 `-O3`가 `-O2`보다 일관되게 7~12% 느리다(범위가 좁음). 원인은 보지 않았다.
- 결론: Quill 처럼 큐를 키워 조건을 맞추는 것은 logx 에 불리하다. 기본 16MB 그대로 비교한다.

**3. 같은 세션 안의 편차는 작지만, 세션 사이의 편차는 크다.**

- 5라운드 안에서는 p50 의 최대/최소 차이가 대부분 10% 안쪽이고(가장 큰 것은 `-O2` 문자열 1T, 128~153ns로 20%), 처리량은 ±1~2%이다.
- 그런데 `LFLOG` 숫자 1T p50 이 이번에는 79~93ns 이다. 11-03 09:36 측정에서는 28ns, 09:17 측정에서는 99ns 였다. 같은 라운드에서 Quill 은 10~11ns 로 11-03 과 같다.
- 머신 전체가 흔들린 것이 아니라 logx 쪽만 두 상태(약 28ns, 약 90ns)를 오가는 것으로 보인다. README 표의 28ns 는 좋은 쪽 상태일 수 있다. TODO 1·2번에서 원인을 찾아야 한다(로깅 스레드 배치, 큐 메모리의 페이지·캐시 배치 등이 후보이고, 아직 안 잼).
