# 시각(TSC)과 busy_poll의 효과

- 날짜: 2026-11-02 14:40~14:51
- 코드: `97bef09`과 같은 코드 (당시 작업 트리). TSC 없음 = 같은 소스를 `-DLF_NO_TSC`로 빌드
- 환경: AMD Ryzen 5 7430U with Radeon Graphics, 12 CPU (6코어 × 2), Linux 6.12.0-211.16.1.el10_2.0.1.x86_64, clocksource=tsc. CPU 10과 11이 같은 물리 코어
- 명령: tsc = `./bench <조건>`, notsc = `-DLF_NO_TSC` 빌드의 `./bench <조건>`, busy = `taskset -c 0-9 ./bench <조건> 11`

## 해석

- 1~2(몰아서 실행): 같은 변형을 3번 연속 돌리고 다음 변형으로 넘어갔더니, 8스레드 버스트에서 TSC가 더 느린 것처럼 나왔다.
- 3(교차 실행): 번갈아 돌리니 두 변형 모두 실행마다 좋을 때와 나쁠 때가 섞였다. 8스레드 버스트는 로깅 스레드 처리량 한계에 가까워 큐가 차느냐에 따라 꼬리 지연이 4µs~140µs로 갈리므로 비교에 쓸 수 없다.
- 4(1·4스레드 교차 5번): 결과는 README "시각(TSC)과 `busy_poll`의 효과" 표다.
  - TSC는 p50을 1스레드 140 → 90ns, 4스레드 80 → 60ns로 줄인다. 꼬리 지연은 그대로다.
  - `busy_poll`은 1스레드 p99.9를 2µs → 0.45µs로 줄인다. 2ms 휴식 뒤 잠든 로깅 스레드를 깨우는 `futex_wake`가 없어졌기 때문으로 보인다.
  - 쉬지 않고 쓸 때 `busy_poll`은 처리량 1.8 → 2.8M줄/s다. 이 조건에서 로깅 스레드는 원래 잠들지 않으므로 전용 코어 덕분으로 보인다.
