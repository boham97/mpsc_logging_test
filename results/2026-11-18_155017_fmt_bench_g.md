## 해석

TODO 3번 첫 단계. `fmt_bench`에 `%g` 항목과 cmp_bench 메시지 세 줄(처리량, 처리량에서 `%g`만 `%zu`로 바꾼 대조군, 지연 numbers)을 추가했다. 커밋 안 된 변경은 `examples/fmt_bench.c`뿐이고 로거 코드는 그대로다.

**1. `%g` 하나가 `snprintf`로 148~165ns 걸린다.** 같은 크기 정수를 `snprintf("%zu")`로 찍으면 27~31ns이니 5~5.5배이고, 직접 변환한 `%d`(6ns)의 약 27배다. `%.17g`는 227ns.

**2. cmp_bench 처리량 메시지의 한 줄 비용 절반이 `%g`다.**

| 메시지 | `render_record` | 포맷팅만 본 상한 |
|---|---|---|
| `"Iteration: %zu int: %zu double: %g"` | 327ns | 3.06 M줄/s |
| 같은 메시지, `%g` → `%zu` (대조군) | 171ns | 5.85 M줄/s |
| 대조군 + 직접 변환 + 해석 캐시 | 78ns | 12.8 M줄/s |

- 포맷팅만 본 상한 3.06 M줄/s는 실제 cmp_bench 처리량 2.98~3.04 M줄/s와 거의 같다. 처리량 상한이 로깅 스레드 포맷팅이라는 것을 숫자로 확인했다(perf 쪽 확인은 [cmp_thr_perf](2026-11-18_155400_cmp_thr_perf.md)).
- `%g`를 정수 비용으로 바꾸기만 해도 156ns(48%)가 빠진다. 거기에 직접 변환·해석 캐시까지 하면 327 → 78ns(4.2배)다. 다만 직접 변환 경로가 `%g`를 지원하지 않으면 `%g` 메시지는 지금 그대로 `render_message`로 넘어가서 효과가 없다.
- "직접" 열이 `%g` 메시지에서 오히려 느린 것(327 → 365ns)은 `all_simple` 검사 후 `render_message`로 되돌아가는 비용이다. 캐시판은 검사 결과를 기억해서 차이가 없다.
- 지연(numbers) 메시지도 308ns로 같은 양상이다.

**3. 결론**: 다음은 `%g` 직접 변환이다. 출력이 `snprintf("%g")`와 글자 하나까지 같아야 하므로(유효숫자 6자리, 지수 표기 전환 기준 `-4 <= exp < 6`, 끝 0 제거, inf/nan/-0) `fmt_test`에 경계값 비교부터 넣는다. 목표는 `%g` 하나를 정수 변환 수준(수십 ns 이하)으로 줄이는 것이다.
