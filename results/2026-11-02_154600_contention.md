# 접두어 직접 변환 후 경쟁이 늘었는가

- 날짜: 2026-11-02 15:46
- 코드: 계측 사본: `lockfree_logger.c`, `async_logger.c`에 카운터 추가(스레드마다 다른 캐시 라인, 로거 close 때 합계 출력). old = `97bef09`의 `log_common.c`, new = `c95baff`의 `log_common.c`
- 환경: AMD Ryzen 5 7430U with Radeon Graphics, 12 CPU (6코어 × 2), Linux 6.12.0-211.16.1.el10_2.0.1.x86_64, clocksource=tsc
- 명령: `./bench 8 200000`을 old/new 번갈아 3번
- 카운터: `cas_fail` = 슬롯 번호 CAS 실패, `cas_stale` = 다른 생산자가 이미 가져간 슬롯을 봄, `full_retry` = 큐가 가득 차 `sched_yield`한 횟수, `futex_wake` = 로깅 스레드 깨우기, `lock_busy` = async 뮤텍스를 바로 못 잡음, `cond_wait` = async 버퍼가 차서 대기

## 해석

| | `LFLOG_TEXT` CAS 실패/호출 | `LFLOG_TEXT` p99 | async 뮤텍스 바로 못 잡음 | async ≥10µs |
|---|---|---|---|---|
| old | 0.88~0.98 | 0.96~1.01 µs | 44~47% | 1.12~1.43% |
| new | **2.44~2.56** | **1.34~1.65 µs** | 46~47% | 0.97~1.49% |

- `LFLOG_TEXT`: 큐는 한 번도 차지 않았다(`full_retry=0`). 늘어난 꼬리 지연은 `enqueue_pos` CAS 경쟁이다. 호출자가 접두어를 빨리 만들어 같은 시간에 CAS를 더 자주 시도한다.
- async: 뮤텍스 경쟁은 그대로이고, 10µs 이상 비율은 범위가 겹친다. 앞의 차이는 편차였다.
- `LFLOG`: CAS 실패는 비슷하고(0.80~0.88 → 0.79~0.80), 큐가 가득 차 재시도한 횟수는 3.1~5.7 → 2.6~2.7회/호출로 줄었다.
- 줄이는 방법: 슬롯 번호를 CAS 대신 `fetch_add`로 받기(`drop_on_full`을 다시 설계해야 함), 또는 스레드별 SPSC 큐.

참고로 같은 시점에 잰 대기 명령 비용이다(CPU 3 고정, 최솟값). `pause`(`_mm_pause`) 15.13ns, `sched_yield` 483.40ns(다른 실행 가능한 스레드가 없을 때). 이 출력은 세션 출력에서 옮겨 적었다.
