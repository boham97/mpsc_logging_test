## 해석

`sudo tools/run_c2c.sh`(`cmp_bench latency lflog string 10000` × 3, `perf c2c record` → `report --stdio -d peer`)의 1번째 실행. 세 실행의 해석을 여기에 모은다.

**결론: 이 머신(Zen3)에서는 perf c2c 로 캐시 라인 경합을 볼 수 없다. 경합이 없다는 뜻이 아니다.**

| 실행 | 1T p50 / 4T p50 | IBS 샘플 | 데이터 출처 해석 불가 | Load L1D / L2 / LLC hit | Peer load | 공유 캐시 라인 |
|---|---|---|---|---|---|---|
| 1 | 118 / 180ns | 593,222 | 402,543 | 82,091 / 31 / 8 | 0 | 0 |
| 2 | 134 / 212ns | — | 402,281 | 82,297 / 17 / 6 | 0 | 0 |
| 3 | 101 / 160ns | — | 402,205 | 82,128 / 34 / 3 | 0 | 0 |

- 샘플의 약 68% 가 "Unable to parse data source" 다. load 의 절반(약 9만)은 "no mapping" 이다.
- Peer(다른 코어 캐시에서 온 load) 는 세 실행 모두 0, 공유 캐시 라인 표는 비어 있다. 로깅 스레드는 호출자가 쓴 슬롯을 반드시 읽으므로 0 일 수 없다. 측정이 안 된 것이다.
- 원인 후보: perf c2c 의 AMD 지원은 Zen4 부터 들어온 IBS 데이터 출처 확장(peer/remote 구분)에 기대는 것으로 안다. Zen3(7430U) IBS 는 이 정보를 주지 않는 것으로 보인다. 아직 문서로 확인하지는 않았다.
- 세 실행이 모두 느린 쪽(1T p50 101~134ns)이라, 빠른 실행과 비교할 거리도 없었다. IBS 샘플링 부하가 지연을 끌어올렸을 수 있다.
- 다음 후보: Zen3 PMU 이벤트 `ls_dmnd_fills_from_sys.int_cache`(같은 CCX 의 다른 L2·L3 에서 채운 demand load) 등을 스레드별로 세서 빠른/느린 실행을 비교한다. 아직 안 잼.
