## 해석

`sudo tools/run_pmu.sh`(`cmp_bench latency lflog string 10000` × 3, `perf stat -a -A -C 0-5 -I 500`, 사용자 모드)의 1번째 실행. 세 실행의 해석을 여기에 모은다.

아래 "메시지 1줄당" 표는 원본 출력 뒤에 같은 CSV(`build/pmu/`, 커밋 안 함)와 같은 구간 분류로 다시 계산했다. 원본 출력의 1000 사이클당 값은 1T 호출 스레드가 `busy_wait`에 쓰는 사이클에 묻혀 읽기 어렵다. 이 계산은 `tools/pmu_summary.py`에 추가해서 다음 실행부터 같이 나온다.

(1T 구간, 200,000줄 기준. `dmnd_ccx` = 같은 CCX 의 L3·다른 코어 L2 에서 채운 demand load)

**1. 클럭은 느린 상태의 원인이 아니다.** 1T 구간 내내 CPU 1(호출)·5(로깅)가 4.33GHz 로 고정이다. 첫 간격의 2.4~2.5GHz 는 스레드가 간격 중간에 시작해서 생긴 값이다. 1T p50 95~127ns 는 최고 클럭에서 나온 숫자다.

**2. 캐시 라인은 메시지 1줄마다 두 코어 사이를 오간다.** 호출 스레드는 1줄당 약 1.1~1.5번, 로깅 스레드는 약 1.4~1.7번 다른 코어 쪽에서 줄을 가져온다. 서로 상대가 방금 건드린 슬롯을 가져오는 것으로 본다(L3 적중이 섞인 근사치). Zen3 CCX 안 코어 간 이동을 1번 약 20ns 로 치면 호출자 쪽만 약 25~30ns/줄이다. 아직 안 잰 추정이다. TODO 2a 가 hot path 비용의 일부라는 것과는 맞는다.

**3. 하지만 실행 간 편차는 설명하지 못한다.** 가장 빠른 실행 3(95ns)의 호출자 `dmnd_ccx`가 1.50 으로 오히려 가장 많다. 세 실행이 모두 느린 상태(95~127ns)라 30~60ns 짜리 빠른 실행과 비교하지 못했다.
- 눈에 띄는 차이는 로깅 스레드 `dmnd_l2`(자기 L2 에서 채움) 7.55 / 5.93 / 2.59 뿐이다. 가장 빠른 실행이 가장 적다. 3번뿐이라 상관이라고 말할 수 없다.

**4. 4T 에서 CPU 4(로깅 스레드와 SMT 짝) 는 `dmnd_l2` 1.3 으로 CPU 2·3(0.5) 보다 많다.** L1 을 나눠 쓰는 영향으로 보인다. 4T 숫자는 TODO 1 과 따로 본다.

다음 후보: 빠른 실행이 나올 때까지 횟수를 늘린다(`sudo tools/run_pmu.sh string 8`). 빠른 실행과 느린 실행의 `dmnd_ccx`·로깅 `dmnd_l2`를 비교한다.
