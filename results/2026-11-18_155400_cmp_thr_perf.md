# cmp_thr_perf

- 날짜: 2026-11-18 15:54 +0900
- 코드: `791731a` + 커밋 안 된 변경 (`examples/fmt_bench.c`만, cmp_bench·로거는 그대로)
- 환경: AMD Ryzen 5 7430U with Radeon Graphics, 12 CPU, Linux 6.12.0-211.16.1.el10_2.0.1.x86_64, clocksource=tsc
- 명령: `perf record -q -e cycles:u --call-graph dwarf,16384 -F 4999 -o thr.data ./cmp_bench throughput lflog`
- 분석: `perf script -F tid,ip,sym --inline` 출력을 `tools/perf_classify.py`로 스레드별·호출 스택별로 집계 (perf.data 는 커밋 안 함)

## 해석

cmp_bench 처리량(`"Iteration: %zu int: %zu double: %g"` 400만 줄, `LFLOG`)을 perf 로 찍었다. perf 아래에서도 처리량은 3.04 M줄/s 로 평소(2.98)와 같다.

- **로깅 스레드 시간의 43.6%가 `%g` 변환(glibc `__printf_fp`)이다.** 잎 함수로 보면 `__printf_fp_buffer_1` 18.4%, `__mpn_divrem` 7.1%, `hack_digit` 5.9%, `__mpn_mul_1` 3.0%, `__mpn_cmp` 2.6%로, glibc 가 다배정도(mpn) 정수 연산으로 십진 자릿수를 뽑는 비용이다.
- 그 밖의 `snprintf`/`vsnprintf`(정수 `%zu` 두 개와 printf 공통 처리)가 25.7%. 스택에 `snprintf`류가 있는 샘플은 모두 합해 67.8%다.
- 메시지 해석(`strchr`, `parse_spec`, `next_arg`)이 17.1%, 접두어 직접 변환은 8.8%.
- 생산자(메인 스레드)는 샘플의 96.5%가 `enqueue_or_wait → sched_yield`, 레코드 기록(`encode_record`)은 0.1%다. 생산자는 거의 늘 빈 슬롯을 기다리고 있으니, 처리량은 로깅 스레드 속도로 정해진다.
- 파일 쓰기는 `cycles:u`(사용자 공간만)라 안 잡힌다. 하지만 [fmt_bench_g](2026-11-18_155017_fmt_bench_g.md)의 포맷팅만 본 상한(3.06 M줄/s)이 실제 처리량과 거의 같으니 쓰기 비용은 작다.
- 결론: TODO 3번 가설이 맞다. `%g`가 가장 크고, 그다음은 정수용 `snprintf`와 포맷 해석이다. `fmt_bench`의 직접 변환 + 해석 캐시 경로에 `%g`를 넣는 것이 다음 단계다.
