# logx — 멀티스레드 환경용 C 로깅 라이브러리

같은 문제(여러 스레드가 하나의 파일에 로그를 쓴다)를 세 가지 설계로 구현하고 비교한다.

| 로거 | 접두어 | 로깅 전용 스레드 | 동기화 방식 |
|---|---|---|---|
| `async_logger` | `alog_` / `ALOG_*` | 있음 | 뮤텍스 + 더블 버퍼 |
| `lockfree_logger` | `lflog_` / `LFLOG_*` | 있음 | 락프리 MPSC 링 버퍼 + futex, **지연 포맷팅** |
| `sync_logger` | `slog_` / `SLOG_*` | 없음 | `O_APPEND` 직접 쓰기(락 없음) 또는 공유 버퍼 + 뮤텍스 |

요구 사항: Linux, GCC(C11), pthread. 락프리 버전은 Linux futex를 직접 쓴다.

## 빌드와 실행

```sh
make                    # liblogx.a, example, bench, fmt_test, fmt_bench, lf_drv
./example               # app_async.log / app_lockfree.log / app_sync.log 생성
./bench 8 200000        # 스레드 8개 × 20만 줄로 전체 모드 비교 + 검증
./bench 8 50000 1000    # 버스트 모드: 1000줄마다 2ms 쉼 (호출 지연 비교용)
taskset -c 0-9 ./bench 8 50000 1000 11  # 락프리 로깅 스레드를 CPU 11 에 고정 + busy_poll
./fmt_test              # 지연 포맷팅 결과가 snprintf 와 같은지 검사
./fmt_bench             # 로깅 스레드의 포맷팅 비용: snprintf vs 직접 변환
make test               # fmt_test + bench 4 50000
make tsan               # ThreadSanitizer 빌드 후 ./bench 4 20000 (libtsan 필요)
make CFLAGS='-O2 -g -std=c11 -DLF_NO_TSC'  # TSC 대신 clock_gettime 으로 시각 저장
make clean
```

`make tsan`을 실행한 뒤에는 바이너리가 TSan 빌드로 남는다. 성능을 측정하려면 `make clean && make`로 다시 빌드한다.

## 로그 형식

```
2026-10-19 16:38:27.349272 [INFO ] 275093 example.c:15 | worker 0 step 0
└─ 로컬 시각(µs)            └ 레벨  └ TID  └ 파일:줄     └ 메시지
```

- 한 줄은 최대 `LOG_LINE_MAX`(1024바이트)이다. 넘으면 잘리고, 끝은 항상 `\n`이다.
- 포맷팅은 호출 스레드의 스택 버퍼에서 락 없이 한다.
- `localtime_r`/`strftime` 결과는 초 단위로 스레드별 캐싱하고, TID도 스레드별로 한 번만 조회한다(이후는 인라인 함수가 TLS 변수만 읽음).
- 접두어는 `snprintf` 없이 직접 쓴다(두 자리씩 표 변환, `memcpy`). 잘릴 수 있는 경우(아주 긴 파일 이름, 작은 버퍼)만 `snprintf`로 넘겨 결과를 같게 한다.
- 타임스탬프는 락이나 큐에 들어가기 전에 찍는다. 그래서 스레드 사이에서는 파일 안의 시각 순서가 조금 뒤바뀔 수 있다. 같은 스레드 안에서는 항상 순서대로다.

## 사용법

```c
#include "logger/async_logger.h"
#include "logger/lockfree_logger.h"
#include "logger/sync_logger.h"

async_logger *a = alog_open("app.log", NULL);        /* INFO, 4MB 버퍼, 200ms, 대기 */
lf_logger    *l = lflog_open("app.log", NULL);       /* INFO, 16384 슬롯, 재시도 */
sync_logger  *s = slog_open("app.log", LOG_INFO, 0); /* 0: 락 없는 직접 쓰기 */

ALOG_INFO(a, "user=%s id=%d", name, id);
LFLOG_ERROR(l, "failed: %s", strerror(errno));   /* 지연 포맷팅: fmt 는 리터럴만 */
LFLOG_TEXT(l, LOG_INFO, dyn_fmt, x);             /* 런타임 포맷 문자열: 호출 스레드가 포맷팅 */
SLOG_WARN(s, "retry %d", n);

alog_flush(a);   /* 지금까지 넣은 로그가 디스크에 써질 때까지 대기 */
alog_close(a);   /* 남은 로그를 모두 쓰고 스레드 종료 */
lflog_close(l);
slog_close(s);
```

매크로는 레벨이 꺼져 있으면 인자를 평가하지 않는다. 런타임에 `*_set_level()`로 레벨을 바꿀 수 있다. 세 로거의 공통 API는 다음과 같다.

| 함수 | 설명 |
|---|---|
| `*_open(path, ...)` | 파일을 `O_APPEND`로 연다. 실패하면 `NULL` |
| `*_write(lg, lv, file, line, fmt, ...)` | printf 형식. 보통은 매크로로 호출 |
| `*_flush(lg)` | 지금까지 넣은 로그를 디스크로 |
| `*_close(lg)` | flush 후 해제 |
| `*_enabled` / `*_set_level` | 레벨 확인/변경 (atomic) |
| `alog_dropped` / `lflog_dropped` | 버퍼나 큐가 가득 차서 버린 개수 |

## 방식 1: 로깅 스레드 + 뮤텍스 더블 버퍼 (`async_logger`)

```
[작업 스레드들] 포맷팅(락 없음) → 락 → front 버퍼에 memcpy → 언락
                                        │ swap (포인터 교환)
[로깅 스레드]   ←───────────────────── back 버퍼 → write() (락 없음)
```

- 호출 스레드는 디스크 I/O를 하지 않는다. 락을 잡는 구간은 `memcpy` 한 번뿐이다.
- 로깅 스레드가 깨어나는 조건:
  - `flush_ms` 주기가 지났을 때
  - 버퍼가 절반 넘게 찼을 때
  - ERROR 이상이 들어왔을 때
- 버퍼가 가득 찼을 때의 동작은 `drop_on_full`로 고른다.
  - `0`: 자리가 빌 때까지 대기한다.
  - `1`: 버리고 개수를 센다. 다음 쓰기 때 `*** dropped N messages ***`를 기록한다.
- `alog_flush()`는 교환 번호(`swap_seq`, `written_seq`)로 "내 로그가 포함된 교환이 디스크까지 갔는지"를 기다린다.
- 조건 변수는 `CLOCK_MONOTONIC`을 써서 시스템 시계 변경에 영향을 받지 않는다.

```c
async_logger_opts o = {
    .min_level = LOG_INFO,
    .buf_size = 8u << 20,   /* front/back 각각 */
    .flush_ms = 100,
    .drop_on_full = 0,
};
```

## 방식 2: 로깅 스레드 없음 (`sync_logger`)

호출 스레드가 직접 쓴다. `buf_size`로 모드를 고른다.

**(a) `buf_size == 0`: 락 없는 직접 쓰기**
- `O_APPEND`로 연 fd에 한 줄당 `write()`를 한 번 호출한다.
- Linux 일반 파일에서 `O_APPEND` write는 오프셋 이동과 쓰기가 원자적이라 줄이 섞이지 않는다.
- 크래시가 나도 이미 호출한 로그는 커널에 넘어가 있다.
- 대신 매 줄 시스템 콜이라 가장 느리다.

**(b) `buf_size > 0`: 공유 버퍼 + 뮤텍스**
- 락을 잡고 버퍼에 `memcpy`한다. 버퍼가 차면 그때 락을 쥔 스레드가 대신 `write()`한다.
- ERROR 이상은 즉시 비운다.
- 단점:
  - 버퍼를 비우는 동안 다른 스레드가 모두 막힌다. 디스크가 느리면 영향이 크다.
  - 백그라운드 타이머가 없어서 로그가 뜸하면 버퍼에 오래 남는다. `slog_flush()`를 직접 불러야 한다.

## 방식 3: 로깅 스레드 + 락프리 MPSC 큐 (`lockfree_logger`)

```
[작업 스레드들] 포맷팅 → CAS로 슬롯 번호 확보 → 슬롯에 memcpy → seq 공개(release)
[로깅 스레드]   seq 확인(acquire) → 로컬 1MB 버퍼에 모음 → write() 한 번
```

- **큐**: Dmitry Vyukov의 bounded MPMC 큐를 소비자 1개로 줄인 것이다.
  - 슬롯마다 `seq` 카운터가 있다.
    - `seq == pos`: 비어 있음 (생산자가 쓸 수 있음)
    - `seq == pos + 1`: 채워짐 (소비자가 가져갈 수 있음)
    - `seq < pos`: 한 바퀴 전 데이터가 남아 있음 → 큐가 가득 참
  - 생산자끼리는 `enqueue_pos` 하나만 CAS로 경쟁한다. 소비자는 혼자라 CAS가 필요 없다.
- **소비자 깨우기 (futex)**:
  - 할 일이 없으면 잠깐 스핀(`pause`)하다가 `futex_wait`로 잔다.
  - 생산자는 평소에 원자 변수 하나만 읽고, 소비자가 자고 있을 때만 `futex_wake`를 호출한다.
  - Dekker 패턴으로 깨우기 유실을 막는다.
    - 생산자: 데이터 공개 → `seq_cst` fence → `sleeping` 확인
    - 소비자: `sleeping = 1` → `seq_cst` fence → 큐 재확인 → 잠
  - 100ms 타임아웃은 안전망이다.
- 큐가 비는 순간 모아 둔 것을 바로 쓴다. 그래서 로그가 뜸해도 지연이 거의 없다.
- **시각 (TSC)**: 호출 스레드는 `rdtsc` 값만 남기고, 실제 시각으로 바꾸는 일은 로깅 스레드가 한다(`clock_gettime` 약 22ns → `rdtsc` 약 8ns).
  - CPU가 invariant TSC를 지원하고 커널 clocksource가 `tsc`일 때만 쓴다. 아니면, 또는 `-DLF_NO_TSC`로 빌드하면 `CLOCK_REALTIME`을 그대로 저장한다.
  - 처음에 10ms 간격 두 쌍으로 주파수를 잡고, 로깅 스레드가 1초마다 (TSC, 실제 시각) 기준점을 다시 잡으며 주파수도 다시 잰다(NTP 보정을 따라감). 비율이 ±0.1% 넘게 튀면 시계 변경(`settimeofday` 등)으로 보고 기준점만 옮긴다.
  - 확인: 5초 동안 20ms마다 남긴 로그의 시각이 호출자가 직접 잰 `clock_gettime`과 ±1µs 안이었고, 뒤로 간 줄이 없었다.
- **`busy_poll`**: 로깅 스레드가 잠들지 않고 큐를 계속 확인한다. 호출자가 `futex_wake`를 할 일이 없어지지만 로그가 없어도 코어 하나를 100% 쓴다. `pin_consumer`/`consumer_cpu`로 전용 코어에 고정해서 쓴다(스레드를 만들 때 고정, 없는 CPU면 `lflog_open`이 `EINVAL`로 실패).
- false sharing을 막으려고 생산자용 변수, 소비자용 변수, 각 슬롯을 64바이트 캐시라인에 정렬했다.

```c
lf_logger_opts o = {
    .min_level = LOG_INFO,
    .capacity = 16384,     /* 슬롯 수, 2의 거듭제곱으로 올림. 메모리 ≈ capacity × 1KB */
    .drop_on_full = 0,     /* 0: sched_yield 하며 재시도, 1: 버림 */
    .busy_poll = 0,        /* 1: 로깅 스레드가 잠들지 않음 (코어 하나 100%) */
    .pin_consumer = 0,     /* 1: 로깅 스레드를 consumer_cpu 에 고정 */
    .consumer_cpu = 0,
};
```

### 지연 포맷팅 (`LFLOG_*`)

Log4j2 Async Logger처럼 문자열 포맷팅을 로깅 스레드로 넘긴다. 호출 스레드는 값만 복사한다.

```
호출 스레드:  LFLOG_INFO(lg, "T%d #%d payload=%s", id, i, str);
              └ _Generic 으로 컴파일 시점에 타입 태그 → {I64,id} {I64,i} {STR,str}
              └ 슬롯: [fmt 포인터][file][시각][TID][레벨][태그+값]...  (문자열만 내용 복사)
로깅 스레드:  fmt 를 해석하며 지정자마다 태그에 맞는 값으로 snprintf → 한 줄 완성
```

- **타입 태그**: `LF_ARG(x)`는 `_Generic`으로 `lf_arg_i/u/f/s/p` 중 하나를 고른다.
  - 정수는 64비트, 실수는 double, `char*`는 문자열, 그 밖의 포인터는 주소로 저장한다.
  - 런타임에 포맷 문자열을 파싱하지 않는다. 구조체 같은 잘못된 타입은 컴파일 에러가 난다.
- **포맷 문자열**: 포인터만 저장한다. 그래서 매크로가 `"" fmt ""` 연결로 리터럴만 받도록 강제한다.
- **printf 형식 검사 유지**: 매크로 안의 `if (0) lf_fmt_check(fmt, ...)`가 `-Wformat` 경고를 그대로 낸다.
- **printf와 같은 결과**:
  - 로깅 스레드는 길이 수식자(`hh h l ll z j t L`)를 떼고, 저장된 타입에 맞는 수식자로 바꿔 끼운다.
  - `hh`/`h`/없음/`l`은 그 폭으로 먼저 잘라서 printf와 결과를 맞춘다(예: `%hhd`에 300 → `44`).
  - `%*d`, `%.*s`, `%%`, 플래그, 폭, 정밀도를 지원한다.
- **문자열 인자**: 호출 시점에 슬롯으로 복사한다. 호출 직후 버퍼를 바꿔도 안전하다.
  - printf처럼 정밀도(`%.5s`, `%.*s`)만큼만 읽는다. NUL이 없는 버퍼(네트워크 패킷 등)도 안전하다.
  - `%s`가 아닌 곳(`%p` 등)에 넘긴 `char*`는 내용을 읽지 않고 주소만 기록한다. `unsigned char*`도 `%s`면 문자열로 출력한다.
  - 이를 위해 문자열/포인터 인자가 있으면 호출 스레드가 포맷 문자열을 훑는다(숫자만 있으면 생략). 호출 위치마다 포맷 문자열과 인자 타입이 고정이므로, 매크로가 호출 위치마다 `static` 캐시를 두고 처음 한 번만 훑는다. `%.*s`의 정밀도는 값이 아니라 "몇 번째 인자인지"를 캐싱해서 호출마다 달라도 된다.
  - 회귀 테스트: `fmt_test`가 문자열 바로 뒤에 접근 금지 페이지를 두고 검사한다. 범위 밖을 읽으면 해당 케이스 이름과 함께 실패한다.
- **제약**:
  - 인자는 최대 16개다.
  - `long double`은 double로 저장한다.
  - `%n`은 무시하고, `%m`은 원문 그대로 출력한다.
  - 슬롯(1KB)을 넘는 인자는 잘리거나 생략된다.
- 런타임에 만든 포맷 문자열에는 `LFLOG_TEXT`를 쓴다. 기존 방식대로 호출 스레드가 `vsnprintf`한다.

**트레이드오프**: 포맷팅 비용이 로깅 스레드 하나에 몰린다.
- 버스트 상황(큐가 넘치지 않음)에서는 호출 지연이 3배 이상 줄어든다.
- 쉬지 않고 쓰는 상황에서는 로깅 스레드가 병목이 된다(이 환경의 `bench` 8스레드에서 약 330만 줄/s, 접두어 직접 변환 전에는 약 180만). 큐가 가득 차면 호출자도 그 속도로 묶인다. 아래 벤치마크 참고.

### 한계
1. **소비자 쪽은 엄밀히 락프리가 아니다.** 슬롯 번호를 확보한 생산자가 데이터를 다 쓰기 전에 선점되면, 소비자는 순서를 지키느라 그 슬롯에서 기다린다.
   - 코어보다 스레드가 훨씬 많고 큐가 가득 차면 꼬리 지연이 커진다. 32 스레드(12코어)에서 최대 50ms까지 관측했다.
   - 큐를 키우거나 `drop_on_full = 1`로 완화할 수 있다.
2. **슬롯이 1KB 고정이다.** 짧은 로그가 많으면 메모리가 낭비된다. 이를 줄이려면 가변 길이 바이트 링 버퍼가 필요하다.
3. `lflog_flush()`는 50µs 간격 폴링으로 구현했다(드문 호출이라고 가정).

## 벤치마크

`./bench`를 12코어 Linux, 로컬 디스크, `-O2`에서 돌린 결과다. 각 줄은 약 120바이트다.

**8 스레드 × 20만 줄 (총 160만 줄)**

| 모드 | 처리량 | 평균 호출 지연 | 최대 지연 |
|---|---|---|---|
| async (뮤텍스 더블 버퍼) | 4.3 M줄/s | 1.7 µs | 0.2~0.8 ms |
| **lock-free (MPSC 링, `LFLOG_TEXT`)** | **11.2~11.8 M줄/s** | **0.59 µs** | **~80 µs** |
| sync direct (O_APPEND) | 0.4 M줄/s | 20 µs | ~0.1~0.2 ms |
| sync buffered (뮤텍스 64KB) | 4.2~4.5 M줄/s | 1.7 µs | 0.2~0.3 ms |

**2 스레드 × 50만 줄**

| 모드 | 처리량 | 평균 | 최대 |
|---|---|---|---|
| async | 5.66 M줄/s | 315 ns | 207 µs |
| lock-free (`LFLOG_TEXT`) | 5.40 M줄/s | 312 ns | **17 µs** |
| sync direct | 0.47 M줄/s | 4.2 µs | 84 µs |
| sync buffered | 4.78 M줄/s | 381 ns | 129 µs |

### 지연 포맷팅 vs 호출 스레드 포맷팅 (lock-free 큐는 동일)

**쉬지 않고 쓸 때** (처리량, 디스크까지)

| 스레드 | async (뮤텍스) | lock-free + 호출자 포맷팅 (`LFLOG_TEXT`) | lock-free + 지연 포맷팅 (`LFLOG`) |
|---|---|---|---|
| 1 | 3.69 M줄/s | 3.50 M줄/s | 3.35 M줄/s |
| 2 | 5.55 | 5.63 | 3.24 |
| 4 | 4.79 | 6.81 | 3.06 |
| 8 | 4.72 | **11.90** | 2.76 |

지연 포맷팅은 로깅 스레드 하나가 포맷팅을 전담하므로 약 300만 줄/s에서 막힌다(접두어 직접 변환 전 측정). 호출자 포맷팅은 포맷팅이 여러 스레드로 분산된다.

**버스트일 때** (`./bench N 50000 1000`: 1000줄마다 2ms 쉼, 큐가 넘치지 않음)

| 스레드 | async (뮤텍스) 평균 / 최대 | `LFLOG_TEXT` 평균 / 최대 | **`LFLOG` 평균 / 최대** |
|---|---|---|---|
| 1 | 485 ns / 371 µs | 676 ns / 52 µs | **196 ns / 49 µs** |
| 4 | 483 ns / 205 µs | 393 ns / 30 µs | **116 ns / 27 µs** |
| 8 | 616 ns / 243 µs | 430 ns / 878 µs | **136 ns / 21 µs** |

실제 서비스처럼 평소엔 조용하다가 몰리는 패턴에서는 지연 포맷팅이 호출자 지연을 3배 이상 줄인다.

### 호출 스레드가 막히는 시간 (호출 지연 분포)

평균과 최대만으로는 얼마나 자주 오래 막히는지 알 수 없어서, `bench`가 호출마다 지연을 기록해 백분위와 10µs 이상 걸린 호출 비율을 출력한다. 시각 측정 비용(약 21ns)이 포함된 값이고, 각 조건을 2번 돌린 범위다.

**버스트, 8 스레드** (`./bench 8 50000 1000`)

| 모드 | p50 | p99 | p99.9 | p99.99 | ≥10µs |
|---|---|---|---|---|---|
| async (뮤텍스) | 310~370 ns | 2.9~4.2 µs | 11~12 µs | 31~42 µs | 0.15~0.19% |
| `LFLOG_TEXT` | 380~390 ns | 1.1~1.2 µs | 1.7~1.8 µs | 7~8 µs | 0.006% |
| **`LFLOG`** | **80 ns** | **0.86~0.93 µs** | **2.0~2.1 µs** | **4.7 µs** | **0.001%** |
| sync direct | 19 µs | 25 µs | 37 µs | 77~83 µs | 91% |
| sync buffered | 340~370 ns | 5.9 µs | 29~31 µs | 50~55 µs | 0.6% |

1, 4 스레드에서도 순서는 같다(`LFLOG` p50 80~120ns).

**쉬지 않고 쓸 때, 8 스레드** (`./bench 8 200000`)

| 모드 | p50 | p99 | p99.9 | p99.99 | ≥10µs |
|---|---|---|---|---|---|
| async | 870~880 ns | 11.5 µs | 20 µs | 34 µs | 1.4~1.5% |
| **`LFLOG_TEXT`** | **570~580 ns** | **1.0 µs** | **1.3 µs** | **4.6~5.0 µs** | **0.002%** |
| `LFLOG` | 1.4~2.9 µs | 13.5~17.9 µs | 29~39 µs | 146~151 µs | 2.4~7.5% |
| sync direct | 20~21 µs | 25~26 µs | 31 µs | 66~69 µs | 99.9% |
| sync buffered | 700~710 ns | 25 µs | 38 µs | 50 µs | 1.9% |

- 뮤텍스 방식(async, sync buffered)은 평균이 비슷해도 1000번에 1번꼴로 10~30µs씩 막힌다(락 대기, 버퍼 교체).
- 큐가 넘치지 않으면 `LFLOG`가 가장 적게 막는다.
- 큐가 가득 차면 `LFLOG`가 가장 많이 막는다. 로깅 스레드의 포맷팅(약 300만 줄/s)이 못 따라가서, 호출자가 빈 슬롯을 `sched_yield`하며 기다린다. 실행마다 편차가 큰 것도 이 대기 때문이다. 이 표는 접두어 직접 변환 전 측정이고, 적용 후는 [접두어 직접 변환 적용 전후](#접두어-직접-변환-적용-전후-bench) 참고. 원인 분석은 [어디서 느린가](#어디서-느린가-perf-bpftrace) 참고.

벤치마크는 끝난 뒤 결과 파일을 다시 읽어서 다음을 검증한다. 모든 모드에서 통과했다.
- 총 줄 수가 맞는지
- 깨진 줄이 없는지
- 스레드별 순번이 `0, 1, 2, …`로 빠짐없이 순서대로인지

### 해석
- 경쟁이 적으면(2 스레드) 처리량은 비슷하다. 락프리는 **꼬리 지연**이 크게 줄어드는 것이 이점이다.
- 스레드가 많을수록 락프리의 이점이 커진다. 뮤텍스는 경쟁이 붙으면 futex로 잠들었다 깨는 비용이 든다.
- 이 벤치마크는 쉬지 않고 쓰는 로컬 디스크 환경이라 sync buffered도 빠르게 나온다. 차이가 나는 경우는 두 가지다.
  - **디스크가 느릴 때** (NFS, fsync 등): sync buffered는 버퍼를 비우는 스레드와 뒤에서 기다리는 스레드가 모두 멈춘다. 로깅 스레드 방식은 로깅 스레드만 기다린다.
  - **로그가 뜸할 때**: 로깅 스레드 방식은 일정 시간 안에 디스크에 써진다. sync buffered에는 그런 보장이 없다.
- sync direct는 느리지만 버퍼가 없어 크래시에 가장 안전하다.

### 로깅 스레드의 포맷팅 비용 (`./fmt_bench`)

지연 포맷팅의 처리량 상한(약 300만 줄/s)이 어디서 오는지 보려고, 로깅 스레드가 레코드 하나를 한 줄로 만드는 비용을 쟀다. 당시의 `render_record`(접두어·메시지 모두 `snprintf`)와, 같은 결과를 내는 직접 변환 버전을 같은 레코드로 비교한다. 아래 표는 그때 측정이다. 이후 접두어 직접 변환은 `log_format_prefix`에 적용했고(70,560개 조합에서 `snprintf` 판과 같음을 `fmt_bench`가 확인), 지금 `fmt_bench`의 "현재" 열은 적용 후 값이다(합계 약 172ns).

- **직접**: 접두어를 `snprintf` 없이 쓰고, 플래그/폭/정밀도 없는 `%d %i %u %x %s`는 직접 변환한다. 그 외 지정자가 있으면 지금의 `render_message`로 넘긴다.
- **직접 + 해석 캐시**: 위에 더해, 포맷 문자열을 "리터럴 조각 + 지정자" 목록으로 한 번만 바꿔 두고 다시 쓴다.
- 측정 전에 직접 변환 결과가 `snprintf`/`render_record`와 글자 단위로 같은지 먼저 확인한다(경계값, `%%`, 길이 수식자, 타입 불일치, 고속 경로가 아닌 포맷 포함). 각 값은 200만 회 × 5번 중 최솟값이다.

**변환 하나** (ns/회)

| 지정자 | `snprintf` | 직접 |
|---|---|---|
| `%d` (1~9자리) | 27.4 | 6.0 |
| `%lld` (1~18자리) | 32.5 | 7.9 |
| `%x` | 27.4 | 4.7 |
| `%s` (43자) | 20.3 | 1.2 |
| `%5d` | 33.4 | 10.0 |

**한 줄 전체** (ns/줄, `"T%d #%d payload=%s"` = bench와 같은 포맷)

| 단계 | 현재 | 직접 | 직접 + 해석 캐시 |
|---|---|---|---|
| 접두어 (시각.us [레벨] TID 파일:줄) | 122 | 23 | 23 |
| 메시지 | 140 | 114 | 50 |
| **합계** | **270** | 140 | **76** |
| 로깅 스레드 상한 (포맷팅만) | 3.7 M줄/s | 7.2 M줄/s | **13.1 M줄/s** |

숫자가 많은 `"req=%u status=%d bytes=%d us=%d id=%x"`는 합계 386 → 121ns (2.6 → 8.2 M줄/s)였다.

- **접두어가 비용의 절반이다.** 줄마다 `snprintf("%s.%06ld [%s] %d %s:%d | ")`를 부르는 비용이다. 지정자가 고정이라 직접 쓰기 쉽다.
- **메시지는 변환만 바꾸면 1.2배밖에 안 빨라진다.** 숫자 변환은 다 합쳐 15ns 정도이고, 나머지는 포맷 문자열 해석(`parse_spec`, `strchr`)에 든다. 해석 결과를 캐싱해야 2.7배가 된다.
- 셋을 다 하면 로깅 스레드 하나로 포맷팅 상한이 약 1300만 줄/s다. `LFLOG_TEXT`가 8스레드에서 낸 1190만 줄/s와 비슷하다. 그래서 포맷팅 전용 스레드를 따로 두는 것보다 이쪽이 먼저다.
- 포맷팅만 잰 값이다. 실제 처리량은 쓰기 비용이 더해져 이보다 낮다.

### 어디서 느린가 (perf, bpftrace)

쉬지 않고 쓸 때 `LFLOG`가 가장 많이 막히는 원인을 확인했다. `bench`는 다섯 모드와 검증·정렬이 프로파일에 섞여서, `LFLOG`만 돌리는 `lf_drv`로 쟀다. `lf_drv`는 호출마다 시각을 재지 않아 `bench`보다 빨리 넣는다.

**CPU 위에서 한 일** (`perf record -e cycles:u --call-graph dwarf ./lf_drv 8 200000`, root 불필요)

| 스레드 | 비중 | 내용 |
|---|---|---|
| 로깅 스레드 | 99% `render_record` | 접두어 `log_format_prefix` → `snprintf` 47%, 메시지 `render_message` → `vsnprintf`·`strchr`·`parse_spec` 49% |
| 호출 스레드 8개 | 94% `sched_yield` | `enqueue_or_wait`에서 빈 슬롯 대기. `encode_record`(실제 일)는 1.5% 미만 |

**CPU 밖에 있던 시간** (`sudo tools/run_bt.sh`, `tools/lf_offcpu.bt`)

| 조건 | 로깅 스레드 | 호출 스레드 (스레드당) |
|---|---|---|
| 쉬지 않고 (`8 200000`, 160만 줄, 0.87초) | `write` 175회 21ms (1MB당 약 120µs, 2.4%), futex 0회, off-CPU 0.5ms | `sched_yield` 39만~52만 회 (줄당 2.3회), futex 1~2회(시작 시점), off-CPU 0.1~0.8ms |
| 1000줄마다 2ms 휴식 (`8 50000 1000`, 40만 줄, 0.13초) | `write` 44회 6ms, futex 1회, off-CPU 0.4ms | `sched_yield` 약 1만 회 (4.7줄당 1회), futex 1~2회, off-CPU 약 103ms (= 2ms 휴식 50번) |

- **병목은 로깅 스레드의 포맷팅 하나다.** 실행 내내 CPU 위에 있고(잠든 적 없음), 디스크 쓰기는 2.4%뿐이다.
- **호출자의 꼬리 지연은 슬롯 대기 루프에서 나온다.** 호출자는 선점되지 않고 CPU 위에서 `try_enqueue` 실패 → 깨우기 시도 → `sched_yield`를 반복한다. 한 바퀴 약 1.8µs (0.87초 ÷ 스레드당 약 47만 회).
- **futex 깨우기는 원인이 아니다.** 로깅 스레드가 잠들지 않으니 호출자가 futex를 부를 일이 없었다.
- `lf_drv 8 50000 1000`은 버스트가 아니다. 초당 400만 줄을 넣어 로깅 스레드 처리량(당시 약 300만 줄/s)을 넘기 때문에 휴식 중에도 큐를 다 비우지 못한다.
- 그래서 [포맷팅 비용](#로깅-스레드의-포맷팅-비용-fmt_bench)의 직접 변환 + 해석 캐시(270 → 76ns/줄)가 이 구간을 직접 줄인다.

**TID 조회 비용** (호출 스레드 쪽, CPU 고정, 1000만 회 × 7번 중 최솟값)

| 방식 | TID 조회 | `encode_record` |
|---|---|---|
| 매번 함수 호출 (스레드별 캐시) | 1.16 ns | 37.9~38.3 ns |
| 인라인 TLS 읽기 (현재) | 0.24 ns | 37.4~37.8 ns |
| 호출자가 인자로 넘김 | 0 | 37.0~37.5 ns |

TID는 스레드마다 한 번만 `gettid`로 받으므로, 인자로 넘겨도 줄어드는 건 함수 호출 1ns 정도다. 측정 편차 수준이고 `LFLOG` 전체(50~170ns, 실행마다 ±30ns)에서는 보이지 않아서 API는 그대로 둔다.

### 시각(TSC)과 `busy_poll`의 효과 (`bench`)

`LFLOG` 모드의 호출 지연. 세 변형을 번갈아 5번씩 돌렸다(몰아서 돌리면 노트북 CPU의 클럭·발열 변화가 한쪽에만 실린다). 값은 5번의 범위이고, `bench`가 호출마다 시각을 재는 비용(약 21ns)이 포함된다.

- **TSC 없음**: `-DLF_NO_TSC` 빌드 (`clock_gettime`)
- **TSC**: 기본 빌드
- **TSC + `busy_poll`**: `taskset -c 0-9 ./bench … 11`. 로깅 스레드를 CPU 11에 고정하고 작업 스레드는 0~9에 둔다. CPU 10은 11과 같은 물리 코어라 비운다(코어 하나를 로깅 전용으로).

**버스트, 1 스레드** (`./bench 1 50000 1000`)

| 변형 | p50 | p90 | p99 | p99.9 | p99.99 | ≥10µs |
|---|---|---|---|---|---|---|
| TSC 없음 | 130~160 ns | 240~270 ns | 410~430 ns | 1.6~2.3 µs | 9.8~15.7 µs | 0.008~0.026% |
| TSC | 90~100 ns | 190~220 ns | 360~400 ns | 1.6~2.3 µs | 9.2~14.0 µs | 0.008~0.014% |
| **TSC + `busy_poll`** | **60 ns** | **60~150 ns** | **180~350 ns** | **450~470 ns** | **0.75~5.7 µs** | **0~0.004%** |

**버스트, 4 스레드** (`./bench 4 50000 1000`)

| 변형 | p50 | p90 | p99 | p99.9 | p99.99 | ≥10µs |
|---|---|---|---|---|---|---|
| TSC 없음 | 80 ns | 140~190 ns | 330~390 ns | 620~740 ns | 3.2~6.0 µs | 0.001~0.009% |
| TSC | 50~60 ns | 80~180 ns | 310~340 ns | 570~920 ns | 2.3~6.1 µs | 0~0.004% |
| TSC + `busy_poll` | 60~70 ns | 150~240 ns | 350~390 ns | 550~650 ns | 1.1~6.3 µs | 0~0.004% |

**쉬지 않고, 8 스레드** (`./bench 8 200000`, 3번씩)

| 변형 | 처리량 | p50 | p99 | p99.99 | ≥10µs |
|---|---|---|---|---|---|
| TSC 없음 | 1.76~1.85 M줄/s | 2.0~3.1 µs | 19~34 µs | 150~167 µs | 5.6~6.4% |
| TSC | 1.75~1.80 M줄/s | 3.0~3.1 µs | 23~24 µs | 149~154 µs | 6.5~7.0% |
| **TSC + `busy_poll`** | **2.74~2.84 M줄/s** | **1.3~1.4 µs** | **15~16 µs** | 143~146 µs | **2.6~3.1%** |

- **TSC는 호출자의 기본 비용을 줄인다.** p50이 1 스레드 140 → 90ns, 4 스레드 80 → 60ns다. 꼬리(p99.9 이상)는 그대로다. 쉬지 않고 쓸 때는 로깅 스레드가 병목이라 차이가 없다.
- **`busy_poll`은 1 스레드의 꼬리를 없앤다.** p99.9가 2µs → 0.45µs다. 2ms 휴식 뒤 잠든 로깅 스레드를 깨우는 `futex_wake`(1000번에 1번)가 사라졌기 때문으로 보인다. 4 스레드에서는 깨우기가 4000번에 1번꼴이라 p99.9 아래로 묻혀 차이가 없다.
- 쉬지 않고 쓸 때 `busy_poll`로 처리량이 1.6배가 된 것은 잠들지 않아서가 아니라 **전용 코어 덕분**으로 보인다. 이 조건에서 로깅 스레드는 원래 잠들지 않는다(위 bpftrace, futex 0회). 고정 없이 돌면 하이퍼스레드 짝을 작업 스레드와 나눠 쓰거나 CPU를 옮겨 다닌다. 작업 스레드가 12개가 아니라 10개 CPU에서 도는 영향도 섞여 있다.
- 8 스레드 버스트(`./bench 8 50000 1000`)는 초당 넣는 양이 로깅 스레드 처리량에 거의 닿아서, 실행마다 큐가 차느냐에 따라 p99.99가 4µs~140µs로 갈린다. 변형 간 비교에 쓸 수 없어 뺐다.

### 접두어 직접 변환 적용 전후 (`bench`)

`log_format_prefix`의 `snprintf`를 직접 변환으로 바꾼 전후. 바꾸기 전(커밋 `97bef09`)과 후를 번갈아 3번씩 돌린 범위다. 모든 실행에서 결과 파일 검증을 통과했다.

**`LFLOG` (로깅 스레드가 접두어를 만듦)**

| 조건 | | 처리량 | p50 | p99 | p99.99 | ≥10µs |
|---|---|---|---|---|---|---|
| 쉬지 않고, 8 스레드 | 전 | 1.73~1.84 M줄/s | 2.9~3.1 µs | 21~24 µs | 152~159 µs | 6.1~6.4% |
| | **후** | **3.28~3.35 M줄/s** | **0.83~0.84 µs** | 23~24 µs | 157~170 µs | **2.9~3.0%** |
| 버스트, 8 스레드 | 전 | 2.93~3.11 M줄/s | 71~110 ns | 3.8~4.6 µs | 43~133 µs | 0.07~0.13% |
| | **후** | **3.48~3.62 M줄/s** | 60~80 ns | **0.69~0.93 µs** | **4.2~5.9 µs** | **0.001~0.002%** |
| 버스트, 1 스레드 | 전 | 0.42~0.43 M줄/s | 80~140 ns | 170~400 ns | 9.6~13.9 µs | 0.008~0.034% |
| | 후 | 0.42~0.43 M줄/s | 90~110 ns | 380~400 ns | 9.8~11.7 µs | 0.010~0.016% |

**호출 스레드가 접두어를 만드는 모드 (p50)**

| 모드 | 버스트 1 스레드 | 버스트 8 스레드 | 쉬지 않고 8 스레드 |
|---|---|---|---|
| `LFLOG_TEXT` | 560~570 → **370~380 ns** | 320~330 → **190~220 ns** | 560~570 → **490~510 ns** (처리량 11.4~12.1 → 12.5~13.2 M줄/s) |
| async | 430~530 → **240~250 ns** | 340~390 → **210~230 ns** | 870~910 → **760~800 ns** |
| sync buffered | 450 → **250 ns** | 330~370 → **220~240 ns** | 720~740 → **650~660 ns** |
| sync direct | 1410 → 1290~1310 ns | 8770~8860 → 8660~8710 ns | 변화 없음 (`write` 시스템 콜이 대부분) |

- **`snprintf`가 병목이었다는 것을 직접 확인했다.** 접두어만 바꿨는데 `LFLOG`의 포화 처리량이 1.9배가 됐다. [어디서 느린가](#어디서-느린가-perf-bpftrace)에서 로깅 스레드 시간의 45%가 접두어 `snprintf`였던 것과 맞는다.
- 실제 로깅 스레드의 줄당 비용은 약 540ns → 약 300ns로, `fmt_bench`로 따로 잰 차이(약 100ns)보다 더 줄었다. 원인은 확인하지 않았다.
- 8 스레드 버스트는 이제 로깅 스레드가 넣는 속도를 따라잡아(약 350만 줄/s) 큐가 차지 않는다. 그래서 꼬리 지연이 1 스레드 수준으로 내려왔다.
- 쉬지 않고 쓸 때 `LFLOG`의 p99와 p99.99는 그대로다. 여전히 큐가 차서 기다리는 호출이 있다. 남은 병목은 메시지 포맷팅(`vsnprintf`와 포맷 문자열 해석)이다.
- 호출 스레드가 포맷팅하는 모드는 p50이 100~200ns 줄었다.
- 바뀌지 않거나 나빠진 것도 있다. 쉬지 않고 쓸 때 `LFLOG_TEXT`의 p99가 0.9~1.0 → 1.3~1.5µs로, async의 10µs 이상 비율이 1.3~1.5 → 1.5~1.6%로 조금 늘었다. 호출자가 빨라져 큐·뮤텍스 경쟁이 늘었을 가능성이 있지만 확인하지 않았다.
- 이 절보다 앞의 벤치마크 표는 모두 이 변경 전 측정이다.

## 어떤 걸 쓸까

| 상황 | 추천 |
|---|---|
| 일반적인 서버, 단순함 우선 | `async_logger` |
| 핫패스에서 로그 지연을 최소화, 로그가 버스트로 몰림 | `lockfree_logger` + `LFLOG_*` (지연 포맷팅) |
| 위와 같고 코어 하나를 로깅에 내줄 수 있음 | 여기에 `busy_poll` + `pin_consumer` (꼬리 지연과 포화 처리량 개선) |
| 스레드가 많고 계속 대량으로 씀 (처리량 우선) | `lockfree_logger` + `LFLOG_TEXT` |
| 스레드를 늘릴 수 없음, 크래시 직전 로그까지 반드시 남겨야 함 | `sync_logger` (a) 모드 |
| 스레드 없이 빠르게, 주기적으로 flush 가능 | `sync_logger` (b) 모드 |

## 검증 상태

- `make tsan`(ThreadSanitizer, 4 스레드 × 2만 줄)에서 **데이터 레이스 경고 없음**. 지연 포맷팅 모드와 `fmt_test`를 포함한다.
- `fmt_test`: 45개 케이스가 `snprintf`와 글자 단위로 일치한다. 정수/실수/문자열/포인터, 플래그·폭·정밀도, `*`, 길이 수식자 잘림, 16개 인자, 호출 후 버퍼 변경, 긴 줄 잘림을 확인한다.
  - 케이스마다 같은 호출 위치를 두 번 부른다(90줄). 첫 호출은 포맷 문자열 분석 캐시를 채우고, 두 번째는 캐시를 쓴다.
  - 범위 밖 읽기 검사: NUL 없는 문자열을 접근 금지 페이지 바로 앞에 두고 `%.*s`, `%.3s`, `%.0s`, `%p`에 넘긴다. 같은 호출 위치에서 `%.*s` 정밀도를 늘려 가며/줄여 가며 불러 캐시가 정밀도 값을 잘못 기억하지 않는지도 본다.
  - 테스트가 버그를 실제로 잡는지 확인: 정밀도 무시, `%p`의 `char*` 내용 복사, 정밀도 값 캐싱, 캐시가 다 채워지기 전에 읽기를 각각 일부러 넣으면 모두 실패한다.
- 컴파일 시점 검사 확인: 형식 불일치는 경고, 리터럴이 아닌 fmt는 에러, 구조체 인자는 에러.
- 단, TSan은 단독 `atomic_thread_fence`를 제대로 모델링하지 못한다. 그래서 락프리 버전의 futex 깨우기(Dekker 패턴)는 TSan으로 증명되지 않았다. 일반 빌드 반복 실행에서는 멈춘 적이 없고, 깨우기가 유실돼도 100ms 타임아웃으로 복구된다.
